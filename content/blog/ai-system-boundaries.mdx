I keep running into the same question when building AI tools: which part of the system should own a decision? Routing a request, executing a tool and keeping track of a coding session need different kinds of state. I’ve been working on those responsibilities in separate projects.

## DMR-X: where should a model request go?

DMR-X handles the gateway and routing layer. An application can connect to model providers through it and leave provider-specific integration to the gateway. The repository has separate code for routing services, provider integrations and the React management interface.

A coding client can keep its own workflow and use DMR-X underneath. Changing a provider should not require rebuilding that workflow.

Sources: [DMR-X overview](https://github.com/danny-dis/dmr-X), [provider management interface](https://github.com/danny-dis/dmr-X/blob/main/apps/ui/src/pages/Providers.tsx).

## MOTE: how should a model-and-tool loop execute?

MOTE is a small Rust execution engine. A run asks a model for an action, checks capability grants, executes a permitted tool and feeds back an observation. Configuration sets execution limits and fallback behavior.

The bridge lets a host application supply Python or TypeScript tools. The application owns its interface, approvals, scheduler and storage. Capability checks limit what the engine permits; they do not provide an operating-system sandbox.

Sources: [MOTE documentation](https://github.com/danny-dis/MOTE), [capability implementation](https://github.com/danny-dis/MOTE/blob/production-ready/src/capability.rs), [bridge process](https://github.com/danny-dis/MOTE/blob/production-ready/src/bin/mote-bridge.rs).

## Chimera: how should a coding workflow be coordinated?

Chimera handles the coding workspace. Its TypeScript packages cover coordination, provider integration, tool loops, context, saved sessions and interfaces. The solo, duo and trio coordinators have separate execution paths.

This layer has to keep track of the coding interaction: its context, tools and session state. A gateway can sit below it without taking over those jobs.

Sources: [Chimera workspace](https://github.com/danny-dis/chimera/tree/main/packages), [duo coordinator](https://github.com/danny-dis/chimera/blob/main/packages/chimera-core/src/coordinator/duo-executor.ts), [trio coordinator](https://github.com/danny-dis/chimera/blob/main/packages/chimera-core/src/coordinator/trio-executor.ts).

## Drift: how should ideas and evidence remain useful?

Drift gives ideas and research a local workspace. A Python backend and React interface handle idea capture, repository context, retained sources and task review.

The interface needs to show whether something is an idea, a proposal or completed work. A research report can retain its citations and still need someone to check them. Approval and implementation are separate steps, and the task state should make that visible.

Sources: [Drift overview](https://github.com/danny-dis/Drift), [dashboard API](https://github.com/danny-dis/Drift/blob/main/drift/ui_api.py), [project and idea state](https://github.com/danny-dis/Drift/blob/main/drift/organism.py).

## Reading the work

The repositories link to implementation files and document their current scope. Some work is an independent build; other repositories are maintained derivatives or architecture specifications. Those labels help explain what you’re looking at. The code and documentation can show how a feature works, but production readiness needs its own testing.
